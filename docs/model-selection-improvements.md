# 모델 선택 개선 기록

웹 화면에서 모델을 골라 기능을 실행할 때, 고른 모델이 실제로 쓰이도록 고친 내용과 그 테스트 결과를 정리한 문서입니다. 작업은 sc4sap 플러그인 0.6.24를 받은 직후인 2026-09-28에 했습니다.

## 먼저, 문제가 무엇이었나

웹의 기능(스킬) 하나를 실행하면 모델이 두 층으로 일합니다.

- **메인(오케스트레이터)**: 질문을 받아 어느 전문가에게 넘길지 정하고, 돌아온 답을 정리합니다. 세션을 열 때 고른 모델이 여기에 쓰입니다.
- **서브 에이전트(전문가)**: 모듈 컨설턴트, 코드 리뷰어, 디버거처럼 실제 조사를 맡는 쪽입니다. 비용 대부분이 여기서 나옵니다.

그런데 플러그인이 두 층 모두 모델을 자기 파일에 박아 두고 있었습니다.

- 스킬 파일(`SKILL.md`)의 `model: sonnet` 같은 줄 때문에, 화면에서 Haiku를 골라도 메인이 중간에 Sonnet으로 바뀌었습니다. 바뀌는 순간 그때까지 쌓은 캐시를 못 쓰고 새로 쓰기 때문에 오히려 돈이 더 들었습니다.
- 에이전트 파일의 `model: opus` 때문에, 전문가는 화면 선택과 상관없이 Opus로 돌았습니다.
- 화면의 "economy"(서브 에이전트를 Sonnet으로 내리는 장치)는 호출에 모델이 직접 적힌 경우만 바꿨습니다. 에이전트 파일에 적힌 Opus는 그대로 통과했습니다.

## 1번 — Ask a Consultant에 모델 선택 추가

**무엇을 했나**

- "컨설턴트에게 묻기"를 처음 실행할 때 모델과 예산을 묻는 창이 뜨도록 했습니다. 기본값은 **Haiku, 예산 $1**입니다.
- 창의 안내문은 영어, 한국어, 일본어로 넣었습니다.

**왜 이제 가능해졌나**

플러그인 0.6.24부터 이 스킬의 설정이 `model: inherit`(세션 모델을 그대로 따름)로 바뀌었습니다. 그래서 Haiku로 세션을 열면 메인이 끝까지 Haiku로 돌고, 모델이 바뀌면서 캐시를 다시 쓰는 비용이 사라집니다. 메인은 질문을 라우팅하고 답을 전달하는 역할이라 Haiku로 충분합니다.

**바뀐 파일**: `web/src/lib/skills.ts`, `web/src/lib/i18n/skills.ts`

## 2번 — economy가 에이전트 파일의 Opus도 잡도록

**무엇을 했나**

- 서브 에이전트를 호출할 때 모델이 적혀 있지 않으면, 플러그인의 `agents/<이름>.md`를 읽어 거기 적힌 모델을 확인합니다. 그게 Opus면 Sonnet으로 내립니다. 이 판단은 `economyDispatch` 함수 하나로 모아서 두 곳(hook, 승인 콜백)이 같이 씁니다.
- Haiku 세션에는 `effort`(생각을 얼마나 깊게 할지)를 보내지 않습니다. Haiku 4.5는 이 옵션을 받지 않아서, Analyze Code처럼 `effort`를 쓰는 기능을 Haiku로 돌리면 실패할 수 있었습니다.

**economy가 켜지는 조건**: 창에서 Opus가 아닌 모델(Haiku, Sonnet)을 고르면 켜집니다. Opus를 고르면 스킬이 원래 원하는 대로 둡니다.

**바뀐 파일**: `src/server/session-manager.ts`

## 3번 — 모델이 고정된 스킬은 세션도 그 모델로 열기

**문제**

"코드 분석"과 "증상 분석"은 스킬 파일에 `model: sonnet`이 박혀 있습니다. 그런데 창에서 Haiku나 Opus를 고르면 세션이 그 모델로 열렸다가 Sonnet으로 바뀌었고, 그때마다 캐시를 새로 썼습니다. 창의 선택은 메인에는 효과가 없으면서 비용만 늘렸습니다. 증상 분석은 기본값이 Haiku여서 매번 이 손해를 봤습니다.

**무엇을 했나**

- 두 스킬에 `pinnedModel: "claude-sonnet-5"`를 지정했습니다. 창에서 무엇을 고르든 세션은 Sonnet으로 열립니다. 그래서 중간에 모델이 바뀌지 않습니다.
- 두 스킬의 창에서는 선택 항목 이름이 **"서브 에이전트 모델"**로 바뀌고, 선택지는 Sonnet과 Opus 두 개만 남습니다. Haiku는 뺐습니다. 메인은 고정이라 효과가 없고, 서브 에이전트는 economy가 Sonnet까지만 내리기 때문입니다.
  - **Sonnet(기본)**: 리뷰어와 디버거가 Sonnet으로 돕니다. 증상 분석이 스스로 Opus로 올리려 해도 Sonnet으로 돕니다.
  - **Opus**: 플러그인이 원래 원하는 대로 둡니다. 코드 리뷰어는 Opus로, 증상 분석은 필요할 때 Opus로 올라갑니다.
- 증상 분석의 기본값을 Haiku에서 Sonnet으로 바꿨습니다. "Haiku가 Sonnet만큼 잘했다"는 예전 근거는, 스킬이 Sonnet을 고정하고 있었으니 사실 Sonnet이 한 결과였을 가능성이 큽니다.
- 창 안내문(영어, 한국어, 일본어)을 실제 동작에 맞게 고쳤습니다. 모델 선택 아래 설명도 "메인은 이 모델, 서브 에이전트는 Opus를 고르지 않으면 Sonnet"으로 바꿨습니다.
- 모델이 고정되지 않은 스킬(컨설턴트에게 묻기)은 전과 같이 Haiku, Sonnet, Opus 셋을 다 보여 줍니다.

**바뀐 파일**: `web/src/lib/skills.ts`, `web/src/components/SkillForm.tsx`, `web/src/lib/i18n/messages.ts`, `web/src/lib/i18n/skills.ts`

**선택 창이 없는 나머지 기능은 손대지 않은 이유**

비교, 스펙 작성, 프로세스 문서, CBO 인벤토리도 스킬이 Sonnet을 고정하지만, 서버 기본 모델이 이미 `claude-sonnet-5`라서 세션이 처음부터 Sonnet으로 열립니다. 모델이 바뀌는 손해가 없습니다. 아래 테스트에서 플러그인의 `sonnet`이 `claude-sonnet-5`와 같은 모델로 처리되는 것도 확인했습니다. 이 기능들에 예산과 economy를 붙이는 건 목록의 4번 작업입니다.

## 3번 테스트

코드 분석을 ZMMR00020(패키지 ZMMPAEK, 관점: 성능)으로, 창에서 "Sonnet"을 고른 것과 같은 조건(세션 Sonnet, economy 켬, effort medium)으로 두 번 돌렸습니다.

| 실행 | 시간 | 비용 | 쓰인 모델 |
|---|---|---|---|
| 1회차 (캐시 없음) | 약 30초 + 백그라운드 리뷰 | $0.82 | Sonnet만 |
| 2회차 (바로 이어서, 캐시 있음) | 87초 | $0.44 | Sonnet만 |

- **확인된 것**: 리뷰어가 Opus 대신 Sonnet으로 돌았고, 메인도 중간에 바뀌지 않았습니다. 사용 내역에 `claude-sonnet-5` 한 줄만 있습니다. 보고서도 정상적으로 나왔습니다(성능 관점 지적 5건).
- **예상과 달랐던 것**: 비용이 줄지 않았습니다. 2026-09-27에 Opus 리뷰어로 같은 조건을 캐시가 있을 때 돌린 기록이 $0.36, 캐시 없을 때가 $0.75였습니다. 이번 Sonnet 리뷰어는 $0.44, $0.82입니다. Sonnet 리뷰어가 글을 더 길게 써서(출력 7.9k 토큰) 단가 차이를 상쇄한 것으로 보입니다. 두 번만 잰 결과라 흔들림이 있을 수 있습니다.
- **그래서**: 코드 분석에서는 "Sonnet이면 싸다"가 아직 증명되지 않았습니다. 기본값을 Opus로 돌릴지, 리뷰어 출력 길이를 줄일지는 몇 번 더 재 보고 정하는 게 좋습니다.
- 증상 분석은 실제 덤프 화면이 필요해서 이번에는 돌리지 않았습니다. 코드는 코드 분석과 같은 경로를 탑니다.
- 창이 브라우저에서 어떻게 보이는지(항목 이름, Haiku 빠짐)는 타입 검사만 했고, 화면으로는 확인하지 않았습니다.

## 4번 — 보류: 각 기능을 개발할 때 같이 붙이기

**결정 (2026-09-28)**: 아래 네 기능은 지금 따로 손대지 않고, 기능을 실제로 개발할 때 이 내용을 같이 반영합니다. `web/src/lib/skills.ts`의 각 항목 위에 이 문서를 가리키는 주석을 달아 뒀습니다.

**지금 상태**: 네 기능 모두 선택 창(`cost`)이 없습니다. 그래서 예산 상한도 economy도 없고, 스킬이 부르는 Opus 에이전트가 그대로 Opus로 돕니다. 스킬은 모두 `model: sonnet` 고정이고, 서버 기본 모델도 Sonnet 5라 메인이 중간에 바뀌는 손해는 없습니다.

| 기능 | 부르는 에이전트 (설정된 모델) | Opus 비용 위험 |
|---|---|---|
| CBO 패키지 인벤토리 (`analyze-cbo-obj`) | sap-stocker (Sonnet) | 없음. 예산 상한만 있으면 됨 |
| 프로그램 비교 (`compare-programs`) | sap-analyst (Opus), sap-code-reviewer (Opus) ×N, sap-writer (Haiku) | 큼. 프로그램 수만큼 리뷰어가 Opus로 돎 |
| 프로그램 → 스펙 (`program-to-spec`) | sap-analyst (Opus), sap-critic (Opus), sap-writer (Haiku) | 있음 |
| 패키지 → 프로세스 (`package-to-process`) | sap-analyst (Opus), sap-stocker (Sonnet), sap-writer (Haiku) | 있음 |

**개발할 때 할 일 (기능마다)**

1. `skills.ts`의 해당 항목에 `cost`를 추가합니다. 코드 분석 항목이 본보기입니다.
   - `pinnedModel: "claude-sonnet-5"`: 스킬이 Sonnet을 고정하고 있으니 세션도 Sonnet으로 엽니다. 창에는 "서브 에이전트 모델"(Sonnet 또는 Opus)이 나옵니다.
   - `defaultModel`: 기본은 Sonnet(economy 켬). Opus가 꼭 필요하다는 측정이 나오면 그때 바꿉니다.
   - `defaultBudgetUsd`: 첫 실측 비용의 2~3배 정도로 잡습니다.
   - `note`: 무엇이 비용을 쓰는지, 선택이 무엇을 바꾸는지 적습니다. 한국어·일본어 문구는 `web/src/lib/i18n/skills.ts`의 `costNote`에 넣습니다.
2. 플러그인이 올라가면 스킬 파일의 `model:` 줄과 에이전트 모델이 바뀌었는지 다시 확인합니다. 스킬이 `model: inherit`로 바뀌었으면 `pinnedModel`을 빼고, 컨설턴트에게 묻기처럼 Haiku·Sonnet·Opus 셋을 다 보여 줍니다.
3. 실제로 한 번 돌려서 사용 내역(`modelUsage`)을 확인합니다. 테스트 스크립트 방식은 위 1·2번 테스트와 같습니다. 백엔드를 켜고 `POST /sessions` → `/messages` → `/stream`의 마지막 `result`를 봅니다.
   - Sonnet을 골랐을 때 Opus 줄이 없어야 합니다.
   - 서브 에이전트가 백그라운드로 돌면 `result`가 두 번 옵니다. 두 번째가 실제 답입니다.
4. 결과를 이 문서에 "4번 — <기능 이름>" 절로 추가합니다.

**주의**: 코드 분석 측정에서는 Sonnet 리뷰어가 Opus 리뷰어보다 싸지 않았습니다(3번 테스트). 비교 기능처럼 리뷰어를 여러 번 부르는 기능은 Sonnet과 Opus를 둘 다 재 보고 기본값을 정하는 게 좋습니다.

### 3번 테스트 보충 — "Sonnet이 더 비싸다"는 착시일 가능성 (2026-09-28)

위 표의 금액은 청구서가 아니라 **Agent SDK가 자체 가격표로 계산한 추정치**입니다. 그런데 SDK(0.3.223)의 가격표는 Sonnet 5를 입력 $3 / 출력 $15로 잡고 있습니다. 공시 가격은 $2 / $10입니다. Opus 4.7은 SDK와 공시 가격이 $5 / $25로 같습니다. 그래서 Sonnet으로 돈 실행만 최대 1.5배 비싸게 표시됩니다.

실제로 캐시 없는 실행($0.82)은 공시 가격으로는 나올 수 없는 금액입니다. 캐시 쓰기를 전부 비싼 요율로 쳐도 약 $0.59가 최대입니다.

| | 캐시 없음 | 캐시 있음 |
|---|---|---|
| Opus 리뷰어 (09-27, SDK 표시) | $0.75 | $0.36 |
| Sonnet 리뷰어 (SDK 표시) | $0.82 | $0.44 |
| Sonnet 리뷰어 (공시 가격으로 환산) | 약 $0.54 | 약 $0.29 |

공시 가격으로 보면 Sonnet이 20~30% 쌉니다. 다만 이것도 계산값이라, 실제 청구 금액은 Console 사용량으로 확인해야 합니다. 그 전까지 "Sonnet이 싸지 않다"는 판단은 보류합니다.

함께 고친 것: 모델 선택 창의 Opus 설명이 "가격 약 5배"였는데, 실제로는 Sonnet의 약 2.5배라 문구를 고쳤습니다(영어·한국어·일본어, 백엔드 목록).

## 5번 — 홈 화면 비용을 공시 가격 기준으로 (2026-09-28)

**무엇을 했나**

- 세션이 끝날 때 기록하는 비용을 SDK 추정치 대신 **Anthropic 공시 가격** 기준으로 계산합니다. 모델별 비용에 보정 계수를 곱하는데, 지금 계수가 다른 모델은 Sonnet 5 하나(×2/3)입니다. 새 파일은 `src/server/pricing.ts`이고, 채팅, 스킬 실행, 홈 화면이 모두 이 값을 씁니다.
- 홈 화면 활동 패널의 큰 숫자를 "이번 주 턴 수"에서 **"이번 주 사용 금액"**으로 바꿨습니다. 턴 수는 아래 목록에 한 줄로 옮겼습니다(이번 주 / 전체).
- 숫자 아래에 "공시 가격 기준이며, 2026-09-28 이전 실행은 SDK 추정치 그대로"라는 안내를 달았습니다. 예전 기록은 모델별 토큰이 저장되어 있지 않아 다시 계산할 수 없습니다.

**왜 Console 실제 청구액이 아닌가**

실제 청구액은 조직 관리자의 Admin API 키로만 읽을 수 있고, 그것도 조직 전체 합계입니다. 모든 계정이 같은 API 키를 쓰는 지금은 사람별로 나눌 수 없습니다. 그래서 사용자에게는 자기 사용분을 공시 가격으로 보여 주고, 실제 청구액 확인은 관리자 기능이 생길 때로 미뤘습니다.

## 6번 — 홈 비용을 월 단위로 (2026-09-28)

**무엇을 했나**

- 활동 패널의 큰 숫자가 **이번 달 1일부터 오늘까지 쓴 금액**입니다. 달이 바뀌면 0부터 다시 쌓입니다.
- 패널 오른쪽 위에 `< 2026.09 >` 버튼을 달았습니다. 이전 달로 가서 그 달 금액을 볼 수 있습니다. 기록이 시작된 첫 달보다 앞으로는 가지 않고, 이번 달보다 뒤로도 가지 않습니다. 주소에 `?month=2026-08`처럼 남아서 새로고침해도 같은 달이 보입니다.
- 기록이 없는 달은 큰 숫자 대신 "이 달에는 비용 사용 내역이 없습니다."라고 표시합니다.
- 아래 목록(대화, 사용 금액, 턴)도 "이번 달(지난 달이면 해당 월) · 전체" 형식으로 바꿨습니다.

**어떻게 계산하나**

- 새 컬렉션 `spend_months`에 계정별·월별 금액, 턴, 대화 수를 쌓습니다. 채팅을 저장할 때마다 **이번 저장으로 새로 늘어난 금액만** 그 달에 더합니다. 그래서 월말에 시작해 다음 달까지 이어진 대화도 각 달에 쓴 만큼 나뉘어 들어가고, 대화를 지워도 월 기록은 남습니다.
- 이 기능 전의 기록은 계정마다 처음 한 번, 기존 채팅을 "마지막으로 사용한 달" 기준으로 옮겨 담았습니다. 예전 채팅은 총액 하나만 있어서 이보다 정확하게 나눌 수는 없습니다.
- 이미 지운 채팅의 금액은 날짜가 남아 있지 않아 어느 달에도 넣지 못했습니다. 그래서 월 금액의 합이 "전체" 금액보다 작을 수 있습니다. 확인한 계정은 9월 $1.39, 전체 $18.45였고, 차이는 대부분 지운 채팅입니다.
- 달의 경계는 웹 서버의 시간대 기준입니다(지금은 한국 시간).
